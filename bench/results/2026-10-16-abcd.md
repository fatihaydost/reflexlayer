# ABCD benchmark: Jev next-button predictions (2026-10-16)

**Data.** ABCD (Action-Based Conversations Dataset): 10,042 customer-service sessions, 30 agent buttons, 36,482 decisions (train 29,190 / dev 3,684 / test 3,608 rows). Distributed in the MIT-licensed asappresearch/abcd repo; there is no separate data licence.

**Label.** The human agent's logged button in a crowdsourced role-play, not policy-optimal. The paper's human volunteer row (Table 3) reports 84.0% next-step and 79.0% button-slot accuracy; the paper does not report how often logged buttons follow the guidelines. In our own count only 34.5% of sessions match the guideline button sequence exactly (bench/spike/abcd/REPORT.md); expect label noise.

**Formulation.** At each point where the agent pressed a button: which button? `decision_type = next_button_after_<last button | none>`, 30 options, context = the dialogue so far including earlier button presses (the decision's own button and everything after it are excluded). The guidelines (kb.json) are not in the context. Types with fewer than 80 calibration (train+dev) sessions were merged into `next_button_after_other` by session count only: make-password, make-purchase, offer-refund, promo-code (31 types became 28). Configs (methods, alphas 0.02/0.05/0.10, delta 0.1, 20 random splits, the 80-session merge rule) were fixed before the Jev run (not verifiable from git history alone).

**Jev run.** `typesafe/jev-1.13`, 36,482 calls (1,000-call pilot, then the rest), total spend $1.693 (pilot $0.046), median latency 331 ms. Errors: 2 transient `HTTPStatusError` rows in the full run, both succeeded on one retry with `--workers 2`; 0 decisions without a successful prediction.

**Findings.**

- Hand-picked fixed 0.9 threshold: serves 13.9% (official) / 13.6% (random), with pooled disagreement 26.5% / 28.7%, far from any small target.
- LTT alpha=0.05: official hb serves 0.4% (held 1/1), wsr serves 1.4% (held 0/1, pooled disagreement 8.0%); random hb serves 0.2% (held 16/16 where served, served in 16/20 splits), wsr serves 0.0% (served in 0/20 splits).
- LTT alpha=0.10: official hb and wsr both serve 3.6% (held 1/1); random hb 3.2% (held 16/20), wsr 3.2% (held 18/20). Alpha=0.02 serves nothing in either view.
- Types served: at alpha=0.05 only next_button_after_pull-up-account (random: 1.3% of its rows under hb); at alpha=0.10 mainly pull-up-account (~16%), plus shipping-status (4.4% of rows, 5/20 splits) and enter-details (~1.2%, 4-5/20 splits); every other type is served in none of the 20 splits. I did not test why these types differ.
- Main served type `next_button_after_pull-up-account` at alpha=0.10: official view 17.4% coverage, 10.7% disagreement, held 0/1 under both hb and wsr (above the 10% budget); random view held 16/20 (hb) and 19/20 (wsr). "Held" is the empirical session-averaged rate on the test half, not the true risk; a train-to-test shift between ABCD splits was not examined.
- Jev top-1 vs baselines (pooled total row, not the guaranteed unit; LTT guarantees each type separately): 43.6% vs last-button 41.8% vs majority 19.7% (official); 44.7% vs 42.5% vs 19.4% (random). Not uniform: S1 is below last-button on `after_none` (63.0% vs 66.4% official) and on every search-* type (e.g. search-faq 5.4% vs 15.9%; search-shirt 3.3% vs 86.3%, random).
- The target of 30-40% coverage at alpha=0.05 is not met (0.0-1.4%).

Notes

- WSR numbers were computed with sessions in sorted-id order (before calibrate.py switched to a keyed-hash order). A review measured on ABCD pull-up-account that 20 hashed orders give WSR thresholds 0.94-0.98 at alpha=0.05 vs 0.95 in id order, and tau retail shows no id trend, so the WSR numbers are not obviously inflated but are order-dependent.
- Held when serving (session avg): test disagreement measured as the mean over served sessions of each session's rate, the quantity LTT bounds; the rows column pools rows instead.
- The total row is pooled over types (not the guaranteed unit): LTT guarantees each type separately, so a per-type guarantee does not imply the total holds.
- Label = the human agent's logged button (MTurk role-play), not policy-optimal. Data distributed in the MIT-licensed asappresearch/abcd repo.
- Official view: calibrate on train+dev sessions, test on test sessions, one run; held when serving is 0/1 or 1/1.
- Random view: seeded 50/50 session splits over one dataset, so the splits are not independent trials.
- Each type is calibrated on its own; total pools all types (coverage per split = served / test rows, then averaged).
- Majority = most frequent button over all calibration rows; last-button = most frequent button for the type in calibration. Both learn from calibration rows only.
